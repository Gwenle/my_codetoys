# TETRIX ARENA

联网对战俄罗斯方块。**Rust 服务端（零第三方依赖）+ 原生 H5 前端**。

核心特色：双方共享**完全相同的方块掉落序列**，消行会给对手最底层塞入**带固定缺口序列**的干扰行并把对手的方块整体上推。对战时双方都能实时看到对方的棋盘。

---

## 玩法

| 机制 | 说明 |
| --- | --- |
| **相同序列** | 双方第 n 个方块永远是同一种形状。序列由服务端用 7-bag 随机一次性生成（3000 个）后下发，两端不可能不一致。 |
| **固定缺口** | 干扰行的缺口列同样来自服务端下发的固定序列（3000 个）。第 k 次收到干扰行，缺口就是序列第 k 项。 |
| **消行即攻击** | 消 1 行 → 对手最底层增加 1 行干扰行；消 2 行 → 2 行；Tetris（4 行）→ 4 行。 |
| **上推** | 收到干扰行时，对手棋盘所有方块整体上移一行，最底层插入新的干扰行；正在下落的方块也会被一起顶上去。 |
| **胜负** | 新方块无处生成、或被干扰行顶出棋盘顶端 → 判负。双方同帧顶出 → 平局。 |
| **向下加速** | 按住 ↓ 软降（20 倍重力），空格硬降。 |

## 按键

| 操作 | 按键 |
| --- | --- |
| 左右移动 | `←` `→`（带 DAS/ARR 自动重复） |
| 向下加速 | `↓` |
| 顺时针 / 逆时针旋转 | `↑` / `X` ；`Z` |
| 硬降 | `空格` |

旋转使用完整 SRS 踢墙表。触屏设备会自动显示虚拟按键。

## 快速开始

```bash
# 1. 编译（零依赖，不需要联网拉包）
cargo build --release

# 2. 启动（默认端口 8787，静态目录 frontend）
./target/release/traix-server --port 8787 --web frontend

# 3. 浏览器打开
open http://127.0.0.1:8787/
```

**本地双人对战**：开两个浏览器标签页，输入**同一个房间号**，两边都点「我准备好了」即可开局。
**局域网对战**：把 `http://<你的局域网IP>:8787/` 发给朋友即可，WebSocket 和页面同源，无需额外配置。

参数：

```
-p, --port <PORT>   监听端口，默认 8787
-w, --web  <DIR>    前端静态资源目录，默认 frontend
```

## 架构

```
┌──────────── 客户端 A ────────────┐        ┌──────────── 客户端 B ────────────┐
│  模拟：自己的棋盘 + 对手的棋盘     │        │  模拟：自己的棋盘 + 对手的棋盘     │
│          （两块都本地模拟）        │        │          （两块都本地模拟）        │
└───────┬──────────────────┬───────┘        └───────┬──────────────────┬───────┘
        │ 按键事件（极少）   │  ▲ tick 时钟             │ 按键事件（极少）   │  ▲ tick 时钟
        ▼                  │  │                        ▼                  │  │
   ┌────────────────────────┴──┴────────────────────────────────────────┴──┴───┐
   │  Rust 服务端：房间管理 + 序列生成 + 60Hz 权威时钟 + 输入转发/哈希转发       │
   │  不做任何游戏模拟 —— 每个房间常驻开销只有两个 mpsc 通道 + 一条定时线程      │
   └───────────────────────────────────────────────────────────────────────────┘
```

### 为什么这么设计

- **省内存 / 省带宽**：服务端不做模拟，只转发按键事件。整局对战跑 1 分钟，上行数据只有几十条几字节的按键消息；对手画面是**本地按确定性模拟算出来的**，不是同步过来的（否则每帧要传两块棋盘）。
- **省内存的 Rust 实现**：`std` + 线程，没有 tokio / axum / serde。二进制 400KB 左右，单个房间常驻开销几百字节。WebSocket 握手（SHA-1 + base64）和帧编解码都是手写的。
- **锁定步（lockstep）**：双方输入都排进「未来」的 tick（`INPUT_DELAY = 5`，约 83ms）生效，所以两台机器的时间轴完全一致，结果逐格相同。
- **回滚重演**：对手输入万一迟到（网络抖动），客户端回滚到自己保存的快照重新推演（保留 360 tick = 6 秒），保证两台机器永远收敛。迟到的输入最多让画面轻微跳一下，不会让两局脱节。
- **不同步自检**：双方每 90 tick 上报一次自己棋盘的哈希，对方用历史哈希逐 tick 比对，UI 上的「同步」指示会立刻变红。

### 一次「消行 → 干扰行」的完整链路（不需要任何网络同步）

```
A 锁定方块 → 判定满行 → 消行 → outGarbage += 1
                                    │
        Match.step() 确定性派发      ▼
   从服务端下发的缺口序列取第 k 项 → B 的模拟：整体上推一行 + 底层插入带缺口干扰行
```

因为两台机器都在本地模拟两块棋盘，这段逻辑在两端得到完全相同的结果，**不需要传任何同步包**。

## 测试

```bash
cargo test            # 序列生成：7-bag 是排列、同种子可复现
node tools/simtest.mjs   # 两台客户端跑同一份输入，逐 tick 比对棋盘哈希
```

`simtest.mjs` 做的事情：

1. **理想网络**：两个 `Match` 实例跑同一份输入（3000+ tick），逐 tick 比对两块棋盘的哈希 → 必须全程一致，且不应发生任何回滚。
2. **抖动网络**：故意让输入迟到（超过 `INPUT_DELAY`），强制走回滚重演路径 → 依然必须逐 tick 收敛。
3. **两个 AI 的真实对局**：一个简易 Dellacherie 评估 AI 打出真实攻防（会消行、会互扔干扰行），再把这份输入用不同延迟喂给两台机器 → 最终棋盘与胜者判定必须一致。
4. **干扰行机制定向验证**：底层插入、恰好一个缺口、缺口来自固定序列、原有方块整体上推、被顶出顶端判负。
5. **完整链路**：`Match` 层消行是否真的变成了对手的干扰行。

## 可调参数

| 位置 | 参数 | 默认 |
| --- | --- | --- |
| `frontend/js/constants.js` | `INPUT_DELAY` | 5 tick，越小越跟手、越大越抗抖动 |
| `frontend/js/constants.js` | `GRAVITY_TABLE` | 每级下落间隔，等级 0 为 24 tick（0.4s/行） |
| `frontend/js/constants.js` | `DAS` / `ARR` / `SOFT_MULT` / `LOCK_DELAY` | 9 / 2 / 20 / 30 |
| `frontend/js/game.js` `lockPiece()` | `this.outGarbage += cleared` | 攻击比例，改成 `+= cleared >= 2 ? cleared - 1 : 0` 即为「消 1 行不攻击」 |
| `src/room.rs` | `SEQ_LEN` / `TICK_MICROS` / `TICK_BROADCAST_MS` | 3000 / 16667 / 25 |
| `src/room.rs` | `SNAPSHOT_KEEP`（在 `constants.js`） | 360 tick 回滚窗口 |

## 已知限制与设计取舍

- **服务端不做裁判**：胜负由两端各自的确定性模拟判定，服务端只负责转发。理论上只要两台机器的 JS 引擎在浮点/整数运算上一致（本项目的模拟只用整数与位运算），结果就一致；已内置哈希自检用于发现并提示异常。
- **后台标签页**：浏览器会冻结后台标签页的定时器和 `requestAnimationFrame`。因此模拟循环由 **Web Worker 心跳**驱动（Worker 定时器不会被冻结），实测切到后台仍以完整速率推进。但如果玩家把标签页挂起很久（超出 6 秒回滚窗口），回来时会被追赶能力兜住，极端情况下仍可能与对手短暂不一致，UI 会提示「同步异常」。
- **断线不重连**：连接断开即退出房间；对局中掉线判对手获胜。没有做断线重连续局。
- **仅两个玩家/房间**，没有观战、匹配队列、排行榜。

## 协议（竖线分隔的文本帧，人肉可读）

客户端 → 服务端：

```
join|ROOM|NAME           加入/创建房间（ROOM 留空则随机开房）
ready|0|1                准备 / 取消准备
in|TICK|ACT|STATE        输入事件，ACT ∈ L R S C W H，STATE ∈ 0 1
hs|TICK|HASH             上报自己棋盘的哈希
dead|TICK                我顶出了
```

服务端 → 客户端：

```
slot|SLOT|ROOM|NAME                分配席位
peer|SLOT|NAME / leave|SLOT        对手进出房间
ready|SLOT|0|1                     准备状态广播
start|SEED|TICK|PIECES_B64|GAPS_B64  开局并下发固定序列
tick|TICK                          权威 60Hz 逻辑时钟（约每 25ms 一次）
in|SLOT|TICK|ACT|STATE             对手输入转发
hs|SLOT|TICK|HASH                  对手哈希转发
end|WINNER|REASON                  对局结束
err|MESSAGE                        错误
```

调试：浏览器控制台里 `__traix` 可以直接看到当前房间/对局状态，例如 `__traix.match.mine.cells`。
